# 1. Objective

Implement the **Chronicle 4 death item/equipment drop system** as a global authoritative gameplay rule.

The system must reproduce the meaningful C4 economic and PvP risk associated with death, including:

- normal PvE death;
- chaotic/red characters;
- PK count;
- equipped items;
- inventory items;
- special protection or eligibility rules for equipped weapons;
- drop count/probability;
- exclusions;
- dropped-item ownership/runtime behavior;
- player/hot-bot/cold-bot equivalence.

This is a **pre-wipe P0 gameplay invariant**.

It is not an optional flavor feature.

---

# 2. Why this matters

Historical Chronicle 4 gameplay included meaningful risk of losing items/equipment on death.

This affected:

```text
PvE risk
PK deterrence
karma management
PK history
equipment value
clan protection
endgame PvP behavior
economic circulation
```

The intended L2Solo world must preserve this pressure.

Bots must face economically equivalent consequences.

Do not implement item-loss only for the human player.

# 7. Idempotency

A death must never duplicate an item drop because of:

```text
duplicate Die callback
worker retry
server restart
session teardown
hot/cold handoff
duplicate persistence proposal
```

Use an idempotent death identity compatible with the death sequence introduced in P0-A if appropriate.

A death drop must resolve at most once.

If the server crashes after inventory removal but before world-drop completion, recovery must not duplicate the item.

Design for restart safety.

# 13. Hot bot behavior

A hot bot must use the exact same drop authority as a human player.

Do not create:

```text
BotDeathItemDrop
```

with different formulas.

Its dropped equipment should become an ordinary world object when the bot is hot/visible.

A bot that loses equipped gear must afterward operate with its actual remaining equipment.

Do not automatically restore replacement gear.

# 14. Cold simulation

Cold bots must face the same economic loss.

However, cold simulation does not need to instantiate a fully visible ground object when no hot world observer exists.

Design an economically equivalent cold outcome.

Possible valid outcomes include:

```text
item removed from bot
+
persistent recoverable world drop
```

or, where current architecture cannot preserve an invisible ground object safely:

```text
item removed from bot
+
authoritative world/economic transfer consistent with existing cold abstraction
```

Prefer preserving the actual dropped item and allowing eventual world recovery if the architecture supports it.

Do NOT simply delete valuable equipment in cold simulation if hot simulation would create a recoverable item, unless that difference is explicitly justified and economically modeled.

Hot/cold outcomes must not create an economic advantage for cold bots.

# 16. Economic conservation

Death drop must be a **transfer/loss-of-possession event**, not item duplication.

For a successfully dropped item:

```text
owner no longer owns it
world/economic state now owns exactly one equivalent instance
```

Never:

```text
owner keeps item
+
ground receives clone
```

Add tests around conservation.

If an item is legitimately destroyed rather than dropped under some rule, that must be explicitly supported by C4 evidence or existing world lifecycle rules.
